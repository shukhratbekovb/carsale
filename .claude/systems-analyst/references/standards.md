# Шпаргалка по стандартам

Сжатый справочник, чтобы артефакты соответствовали реальной практике ИТ-компаний, а не «общим словам».

---

## ISO/IEC/IEEE 29148:2018 — требования

Действующий международный стандарт инженерии требований; заменил IEEE 830-1998.
Определяет три уровня документов требований:

- **StRS** (Stakeholder Requirements Specification) — требования стейкхолдеров, «что нужно бизнесу».
- **SyRS** (System Requirements Specification) — требования к системе в целом.
- **SRS** (Software Requirements Specification) — требования к ПО.

Свойства хорошего требования (по стандарту): необходимое, однозначное, полное, единичное,
проверяемое (testable), непротиворечивое, осуществимое, трассируемое.

Форма записи: субъект + «shall / система должна» + действие/ограничение + условие.
Пример: «Система должна отклонять вход после 5 неудачных попыток в течение 15 минут».

Условие-действие, таблицы решений и use cases — допустимые способы фиксации требований.

Обязательные практики: уникальные ID, acceptance criteria, RTM (трассируемость), запрет
непроверяемых слов («быстро», «удобно», «надёжно») без метрики.

---

## Use Case (шаблон Коберна / Cockburn)

Уровни целей: «цель пользователя» (sea level) — основной уровень для UC; «подфункция» (ниже);
«стратегический» (выше). Большинство UC пиши на уровне пользовательской цели.

Обязательные поля: основной актёр, заинтересованные стороны и интересы, предусловия, постусловия
(гарантии успеха), триггер, основной поток, альтернативы, исключения.

Основной поток — нумерованные шаги «актёр делает → система отвечает». Альтернативы и исключения
привязаны к номеру шага (2a, 2b…).

UML-связи use case: include (обязательное включение общего поведения), extend (опциональное
расширение), generalization (наследование актёров/UC).

## C4 model — архитектура

Четыре уровня абстракции (зум сверху вниз):

1. **Context** — система как чёрный ящик + пользователи и внешние системы. Аудитория: все.
2. **Container** — приложения/сервисы/БД/очереди внутри системы и связи между ними.
   «Контейнер» = отдельно запускаемая/деплоимая единица (а не Docker-контейнер).
3. **Component** — декомпозиция контейнера на компоненты/модули.
4. **Code** — классы (обычно НЕ документируют вручную: быстро устаревает, генерируется из кода).

C4 описывает только статическую структуру. Для динамики (поведение) бери UML sequence.

---

## arc42 — структура документа архитектуры

Шаблон из 12 разделов (используй облегчённо, не ради формы):

1. Введение и цели · 2. Ограничения · 3. Контекст и границы (← C4 Context) ·
4. Стратегия решения · 5. Building Block View (← C4 Container/Component) ·
6. Runtime View (← sequence/activity) · 7. Deployment View · 8. Сквозные концепции ·
9. Архитектурные решения (← ADR) · 10. Качественные требования (← NFR) ·
11. Риски и техдолг · 12. Глоссарий.

Маппинг C4 ↔ arc42: Context → гл.3, Container → гл.5 ур.1, Component → гл.5 ур.2,
динамика → гл.6, deployment → гл.7.

В этом навыке arc42 распределён по файлам пакета (архитектура — в 09, NFR — в 05, риски — в 12,
глоссарий — в 01, ADR — в 14), а не в одном огромном документе.

## ADR — Architecture Decision Record

Короткая запись одного значимого решения: Контекст → Решение → Последствия → Альтернативы.
Статусы: Proposed / Accepted / Superseded. Один файл = одно решение, нумерация сквозная.
Документируй решение, когда: сделан значимый технологический выбор, решена крупная проблема,
введён риск, выбрана из нескольких альтернатив.

---

## RTM — Requirements Traceability Matrix

Связывает цепочку: потребность/цель → требование → дизайн/use case → реализация → тест.
Зачем: гарантирует, что каждая цель покрыта, каждое требование протестировано, ничего лишнего.
Двунаправленная трассируемость: вперёд (цель → тест) и назад (тест → цель).
Пробелы в матрице — ценный результат: показывают непокрытые цели и осиротевшие требования.

## Практические ориентиры (что реально делают в ИТ-компаниях)

- Для современных SaaS оптимум: **C4-диаграммы + несколько ADR + лёгкие markdown-шаблоны**, а не
  тяжёлый формализм ради формализма.
- Документация-как-код: всё в markdown в репозитории, диаграммы как текст (Mermaid/PlantUML) —
  диффится, ревьюится, версионируется вместе с кодом.
- Не документируй уровень Code и слишком детальные вещи, которые меняются каждый день.
- Аналитик ценен не объёмом бумаг, а **трассируемостью, выявленными пробелами и непротиворечивостью**.
- Глубину масштабируй под сложность: для простого продукта — кратко, для сложного — детально,
  но состав пакета держи полным и предсказуемым.
