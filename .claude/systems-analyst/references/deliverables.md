# Шаблоны артефактов

Структура каждого документа пакета. Используй как каркас, наполняй содержанием из PRD.
Везде веди сквозные ID и ссылки между документами (трассируемость).

Соглашение по ID:
- Цели: `G-1`, `G-2`… (из PRD)
- Функциональные требования: `FR-1`, `FR-2`…
- Нефункциональные: `NFR-1`…
- Use cases: `UC-01`…
- Сущности данных: имена в `UPPER_CASE` в ER, в тексте — как есть
- ADR: `ADR-001`…

Общий заголовок каждого документа:

```markdown
# <Продукт> — <Название документа>

> Версия: 1.0 · Дата: <YYYY-MM-DD> · Источник: [PRD](../PRD.md) · Автор: Системный аналитик
```

## 00 — План анализа и проекта (`00-analysis-plan.md`)

Точка входа в пакет. Должен дать читателю карту: что проанализировано, как организовано, куда идти.

```markdown
## 1. Краткое резюме
2–3 абзаца: что за продукт, какую проблему решает, что охватывает этот пакет аналитики.

## 2. Объём и подход
- Что входит в анализ, что вынесено за рамки (out of scope).
- Методология: ISO/IEC/IEEE 29148 (требования), C4+arc42 (архитектура), UML (поведение).
- Ключевые допущения верхнего уровня.

## 3. Состав пакета
Таблица-оглавление со ссылками на все документы пакета и строкой описания каждого.

## 4. Дорожная карта анализа → разработки
Как артефакты этого пакета связаны с фазами разработки (что нужно прежде чем кодить).

## 5. Открытые вопросы верхнего уровня
Список с владельцем ответа (Product / Tech Lead / Заказчик).
```

## 01 — Глоссарий и доменная модель (`01-glossary-domain-model.md`)

Единый язык (ubiquitous language) + статическая структура домена.

```markdown
## 1. Глоссарий
Таблица: Термин | Определение | Синонимы | Примечание.
Включай все доменные понятия, упомянутые в PRD, плюс выявленные при анализе.

## 2. Доменная модель
Class- или ER-диаграмма ключевых сущностей домена и их связей (см. diagrams.md).
Это концептуальный уровень (не физическая схема БД — она в 08).

## 3. Бизнес-правила
Нумерованный список правил предметной области (BR-1, BR-2…), которые система обязана соблюдать.
Каждое правило позже отражается в требованиях.
```

## 02 — Стейкхолдеры, актёры и роли (`02-stakeholders-actors.md`)

```markdown
## 1. Стейкхолдеры
Таблица: Стейкхолдер | Интерес/цель | Влияние (выс/сред/низ) | Как учтён в продукте.

## 2. Актёры системы
Таблица: Актёр | Тип (человек/внешняя система/время) | Описание | Основные цели.
Актёры — это участники use case модели. Имена должны совпадать с UC-документом.

## 3. Роли и модель доступа
Таблица ролей и их прав (что роль может/не может). Основа для авторизации и для UC.

## 4. RACI по ключевым активностям проекта (опционально)
Матрица: Активность × Роль = R/A/C/I.
```

## 03 — Use case модель (`03-use-case-model.md`)

Сердце поведенческого анализа. Диаграмма + детальные спецификации по Cockburn.

```markdown
## 1. Диаграмма use cases
Use case диаграмма (PlantUML — см. diagrams.md). Покажи всех актёров, границу системы,
use cases и связи (association, include, extend, generalization).

## 2. Реестр use cases
Таблица: ID (UC-01) | Название | Основной актёр | Приоритет (P0/P1/P2) | Цель PRD (G-x).

## 3. Детальные спецификации
Для каждого значимого use case — по шаблону Cockburn:
```

Шаблон одного use case:

```markdown
### UC-03: <Название>

- **ID:** UC-03
- **Основной актёр:** <актёр>
- **Заинтересованные стороны и интересы:** <кто и что хочет>
- **Уровень:** пользовательская цель / подфункция
- **Триггер:** <что запускает сценарий>
- **Предусловия:** <что верно до начала>
- **Постусловия (гарантии успеха):** <что верно после успешного завершения>
- **Связанные требования:** FR-5, FR-6 · **Цель PRD:** G-2

**Основной поток (happy path):**
1. Актёр …
2. Система …
3. …

**Альтернативные потоки:**
- 2a. <условие>: <шаги>

**Исключения / ошибки:**
- 2b. <ошибка>: <как система реагирует>

**Частота / нагрузка:** <как часто выполняется>
**Открытые вопросы:** <если есть>
```

Минимум — детально расписать все P0 use cases; P1/P2 можно короче, но в реестре указать все.

## 04 — Функциональные требования (`04-functional-requirements.md`)

SRS-стиль по ISO/IEC/IEEE 29148. Каждое требование — проверяемое, с ID и acceptance criteria.

```markdown
## 1. Обзор
Как организованы требования (по функциональным модулям / по use cases).

## 2. Требования
Группируй по модулям. Для каждого требования:
```

Шаблон требования:

```markdown
### FR-12: <Краткое название>

- **Формулировка:** Система должна <что именно> при <условие>.
- **Приоритет:** P0 / P1 / P2
- **Источник:** UC-03, G-2, BR-4
- **Входы:** <данные/события>
- **Обработка:** <что происходит>
- **Выходы:** <результат/реакция>
- **Acceptance criteria (Gherkin или чек-лист):**
  - Дано <контекст>, когда <действие>, тогда <ожидаемый результат>.
  - …
- **Зависимости:** FR-9
```

Правило: никаких непроверяемых формулировок. Если нельзя написать acceptance criteria — требование
сформулировано плохо, переформулируй.

## 05 — Нефункциональные требования (`05-nonfunctional-requirements.md`)

```markdown
Сгруппируй по категориям, каждое NFR с ID, метрикой и способом проверки.

## 1. Производительность
NFR-1: Время отклика API p95 < 300 мс при нагрузке N RPS. Проверка: нагрузочный тест.

## 2. Масштабируемость
## 3. Надёжность и доступность (SLA, RTO/RPO)
## 4. Безопасность (аутентификация, авторизация, шифрование, аудит, OWASP)
## 5. Приватность и соответствие (GDPR/152-ФЗ и т.п., если применимо)
## 6. Совместимость (платформы, браузеры, устройства)
## 7. Доступность (accessibility, WCAG, если применимо)
## 8. Наблюдаемость (логи, метрики, трейсинг)
## 9. Локализация / интернационализация (если применимо)
```

Каждый пункт — измеримая метрика + метод верификации. Без «система должна быть безопасной».

## 06 — Sequence-диаграммы (`06-sequence-diagrams.md`)

```markdown
Для каждого ключевого сценария (обычно = P0 use case) — sequence-диаграмма (Mermaid, см. diagrams.md).

### 6.1 <Сценарий> (реализует UC-03)
- Краткое описание сценария.
- ```mermaid sequenceDiagram … ```
```

## 07 — Процессы и состояния (`07-process-and-state.md`)

```markdown
## 1. Бизнес-процессы (activity)
Для сквозных процессов — activity-диаграмма (Mermaid flowchart, см. diagrams.md):
дорожки/ответственные, ветвления, параллельные ветки.

## 2. Жизненный цикл сущностей (state machine)
Для сущностей с нетривиальным жизненным циклом (Заказ, Заявка, Платёж) — state-диаграмма:
состояния, события-переходы, действия. Состояния должны согласоваться со статусами в модели данных (08).
```

## 08 — Модель данных (`08-data-model.md`)

```markdown
## 1. ER-диаграмма
Логическая модель данных (Mermaid erDiagram, см. diagrams.md): сущности, атрибуты, связи,
кардинальность.

## 2. Словарь сущностей
Для каждой сущности — таблица атрибутов: Атрибут | Тип | Обяз. | Описание | Ограничения.

## 3. Ключевые связи и ограничения целостности
Списком: внешние ключи, уникальность, каскады, важные индексы (на уровне логики, не DDL).

## 4. Замечания по объёму и росту данных
Ожидаемые объёмы, что растёт быстро — вход для решений по хранению/шардированию.
```

## 09 — Архитектура (`09-architecture.md`)

C4 в структуре arc42 (облегчённой). Не пытайся документировать уровень Code — он быстро устаревает.

```markdown
## 1. Цели и ограничения архитектуры
Качественные атрибуты (из NFR), технические и организационные ограничения.

## 2. Контекст системы (C4 Level 1)
Диаграмма System Context: система, пользователи, внешние системы (см. diagrams.md).

## 3. Контейнеры (C4 Level 2)
Диаграмма Container: приложения, сервисы, БД, очереди и протоколы между ними.
Таблица контейнеров: Контейнер | Технология | Ответственность.

## 4. Компоненты ключевых контейнеров (C4 Level 3)
Для самых важных контейнеров — компонентная декомпозиция.

## 5. Сквозные концепции (cross-cutting)
Аутентификация/авторизация, обработка ошибок, логирование, конфигурация, транзакции.

## 6. Развёртывание (deployment, высокий уровень)
Где что крутится (cloud/on-prem, окружения), как масштабируется.

## 7. Архитектурные решения
Список ссылок на ADR (см. 14-adr/). Каждое значимое решение — отдельный ADR.
```

## 11 — Матрица трассируемости (`11-traceability-matrix.md`)

```markdown
## RTM
Таблица, связывающая всё в сквозную цепочку:

| Цель PRD | Требование | Use case | Диаграмма | Тест/критерий приёмки | Статус |
|----------|------------|----------|-----------|-----------------------|--------|
| G-1 | FR-1, FR-2 | UC-01 | 06 §6.1 | TC-1 | покрыто |
| G-2 | FR-5 | UC-03 | 06 §6.2 | TC-4 | пробел: нет UC |

Правила:
- Каждая цель PRD должна вести хотя бы к одному требованию.
- Каждое требование должно быть покрыто use case и/или тестом.
- Строки с пробелами явно помечай — это ценный результат анализа.
```

## 14 — ADR (`14-adr/ADR-001-<тема>.md`)

По одному файлу на значимое архитектурное решение. Классический шаблон:

```markdown
# ADR-001: <Решение>

- **Статус:** Предложено / Принято / Заменено ADR-00X
- **Дата:** <YYYY-MM-DD>

## Контекст
Проблема и факторы, влияющие на решение.

## Решение
Что решили делать.

## Последствия
Что становится проще, что сложнее, какие риски вводим и как митигируем.

## Рассмотренные альтернативы
Кратко: что ещё рассматривали и почему отклонили.
```
