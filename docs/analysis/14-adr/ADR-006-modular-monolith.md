# ADR-006: Модульный монолит как стартовая архитектура

- **Статус:** Принято
- **Дата:** 2026-06-28
- **Автор:** Системный аналитик

---

## Контекст

При проектировании бэкенда Carsale необходимо выбрать архитектурный стиль. Варианты: монолит, модульный монолит, микросервисы.

Контекст проекта:
- Стартап, MVP-стадия; команда 3–5 разработчиков
- Бизнес-домен ещё уточняется (границы сервисов могут меняться)
- Требование горизонтального масштабирования для ML-inference и каталога (NFR-7)
- ML-компонент исторически требует отдельного деплоя (Python-стек vs Node.js/Go)

---

## Решение

**Core бизнес-логика:** модульный монолит на Node.js/TypeScript (или Python FastAPI) с чёткими модульными границами:
- Auth Module
- Listing Module
- Chat Module
- Payment Module
- Notification Module
- User Module
- Admin Module

Каждый модуль — отдельный директорий с собственными контроллерами, сервисами, репозиториями. Межмодульное общение **только через публичный интерфейс** модуля (не прямой доступ к БД другого модуля).

**ML Service:** отдельный контейнер (Python FastAPI) — исключение из монолита, обоснованное технологическим стеком (Python ecosystem для ML). Взаимодействие: REST/HTTP (синхронно) + Message Queue (асинхронно).

**Граница разделения на сервисы:** при достижении нагрузки > 5 000 RPS или при необходимости независимого деплоя конкретного модуля — выделить в отдельный сервис. Граница уже определена модульной архитектурой.

---

## Последствия

**Что становится проще:**
- Простота разработки и отладки на старте (один процесс, одна БД, простые транзакции)
- Единый deployment pipeline
- Нет проблемы network latency между сервисами (кроме ML)
- Легко рефакторить границы модулей без network contract
- Найм: один язык/стек для бэкенд-разработчиков

**Что становится сложнее:**
- При большой команде (> 10 разраб.) — конфликты в одном репозитории
- Горизонтальное масштабирование = масштабируется весь монолит (не только узкое место)

**Митигация сложностей масштабирования:**
- Stateless монолит (сессии в Redis) → горизонтальное масштабирование через Load Balancer возможно уже сейчас
- Read replicas PostgreSQL для read-heavy endpoints (каталог)
- Redis кэш снимает нагрузку с БД
- При bottleneck: выделить Listing Module первым (наиболее нагруженный)

## Рассмотренные альтернативы

| Альтернатива | Причина отклонения |
|-------------|-------------------|
| **Классический монолит (без модульности)** | Сложнее разделить на сервисы потом; технический долг накапливается быстрее |
| **Микросервисы с первого дня** | Overhead: service mesh, distributed tracing, network contracts, distributed transactions — для команды из 3–5 человек это замедляет разработку в 2–3 раза; преждевременная оптимизация |
| **Serverless (AWS Lambda / UZ аналог)** | Нет зрелых serverless-платформ в UZ; cold start для ML неприемлем |
| **Event-driven (Kafka-first)** | Избыточная сложность для MVP; очередь для async (RabbitMQ) достаточна |

---

## Правило перехода к микросервисам

Выделять модуль в отдельный сервис ТОЛЬКО при выполнении одного из:
1. Модуль регулярно является bottleneck при нагрузочных тестах, и горизонтальное масштабирование монолита неэффективно
2. Модуль требует отдельный цикл деплоя (несколько раз в день) без затрагивания остального кода
3. Команда вырастает до 8+ разработчиков и появляется 2+ продуктовые команды с независимыми roadmap
