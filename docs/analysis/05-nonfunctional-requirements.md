# Carsale — Нефункциональные требования (NFR)

> Версия: 1.0 · Дата: 2026-06-28 · Источник: [PRD](../PRD.md) · Автор: Системный аналитик  
> Стандарт: ISO/IEC/IEEE 29148:2018

---

## 1. Производительность

### NFR-1: Время отклика каталога и карточки

- **Требование:** Система должна отвечать на запросы каталога объявлений и страниц объявлений за ≤ 2 сек (p95) при нагрузке 10 000 одновременных сессий.
- **Метрика:** p95 latency API-эндпоинтов `/listings` и `/listings/{id}` ≤ 2 000 мс при 10 000 concurrent users
- **Условие:** результаты измеряются на эмулированном соединении 4G (≥ 10 Мбит/с)
- **Метод проверки:** нагрузочный тест (k6 / Locust): ramp-up до 10 000 VU, steady-state 5 мин

### NFR-2: Время отклика ML-inference (Deal Rating)

- **Требование:** Система должна возвращать Deal Rating за ≤ 1 сек (p95) для одного объявления.
- **Метрика:** p95 latency ML-inference endpoint ≤ 1 000 мс
- **Метод проверки:** нагрузочный тест ML-сервиса: 100 RPS, p95 latency

### NFR-3: Время обработки фото (блюр)

- **Требование:** Система должна возвращать blurred-версию одного фото за ≤ 5 сек (p95).
- **Метрика:** p95 latency blur API ≤ 5 000 мс для файла ≤ 10 МБ
- **Метод проверки:** автотест с типовой выборкой фото (100 файлов разных размеров)

### NFR-4: Время загрузки главной страницы

- **Требование:** Система должна обеспечивать загрузку главной страницы ≤ 2 сек на соединении 3G (1.6 Мбит/с).
- **Метрика:** Largest Contentful Paint (LCP) ≤ 2 000 мс на 3G (Chrome DevTools throttle)
- **Метод проверки:** Lighthouse CI (LCP в бюджете), реальное устройство на 3G-соединении

### NFR-5: OTP-доставка

- **Требование:** SMS OTP должно доставляться пользователю за ≤ 30 сек в 95% случаев.
- **Метрика:** p95 delivery time ≤ 30 000 мс (измеряется Eskiz UZ delivery receipts)
- **Метод проверки:** мониторинг delivery rate на прод; alert при деградации

### NFR-6: Платёжная обработка

- **Требование:** Система должна обрабатывать успешный платёж (получение webhook + обновление статуса) за ≤ 5 сек.
- **Метрика:** p95 webhook processing time ≤ 5 000 мс
- **Метод проверки:** интеграционный тест с sandbox Click/Payme

## 2. Масштабируемость

### NFR-7: Горизонтальное масштабирование

- **Требование:** Сервисы каталога и ML-inference должны масштабироваться горизонтально (добавление инстансов) без изменения кода.
- **Метрика:** добавление 2× инстансов должно обеспечить 1.8× прирост пропускной способности (efficiency ≥ 90%)
- **Метод проверки:** нагрузочный тест с масштабированием fleet

### NFR-8: CDN для медиа-файлов

- **Требование:** Все фото объявлений должны раздаваться через CDN с edge-узлом в Узбекистане.
- **Метрика:** p95 latency загрузки одного фото (≤ 300 КБ thumbnail) ≤ 500 мс из Ташкента
- **Метод проверки:** curl timing из Ташкентского IP

### NFR-9: Объём данных

- **Требование:** Система должна корректно работать при объёме 1 000 000 объявлений в БД без деградации производительности.
- **Метрика:** p95 latency каталога при 1 млн записей ≤ 2 сек (NFR-1)
- **Метод проверки:** тест производительности на данных с синтетически генерированным объёмом

---

## 3. Надёжность и доступность

### NFR-10: Uptime платформы

- **Требование:** Система должна обеспечивать uptime ≥ 99.5% в месяц (допустимый плановый и внеплановый простой ≤ 3 час 38 мин / месяц).
- **SLA:** 99.5% monthly uptime
- **RTO (Recovery Time Objective):** ≤ 30 мин (время восстановления после отказа)
- **RPO (Recovery Point Objective):** ≤ 1 час (максимально допустимая потеря данных)
- **Метод проверки:** мониторинг uptime (UptimeRobot / Grafana); monthly SLA отчёты

### NFR-11: Резервное копирование

- **Требование:** Резервные копии БД должны создаваться не реже 1 раза в час и храниться ≥ 30 дней.
- **Метрика:** восстановление из резервной копии выполняется ≤ 1 час (RPO ≤ 1 час)
- **Метод проверки:** ежеквартальный drill восстановления из backup в staging-среде

## 4. Безопасность

### NFR-12: Шифрование данных в транзите

- **Требование:** Все данные между клиентом и сервером и между внутренними сервисами должны передаваться по TLS версии ≥ 1.2.
- **Метрика:** 0 незашифрованных соединений; сертификаты действительны; TLS 1.0/1.1 отключены
- **Метод проверки:** SSL Labs scan (Score A или A+); автопроверка срока сертификата

### NFR-13: Шифрование данных в покое

- **Требование:** Базы данных и файловое хранилище должны использовать AES-256 шифрование для данных в покое.
- **Метрика:** все тома БД и S3-совместимое хранилище зашифрованы AES-256
- **Метод проверки:** проверка конфигурации хранилища при деплое (IaC audit)

### NFR-14: Rate limiting API

- **Требование:** Все публичные API-эндпоинты должны иметь rate limiting для защиты от парсинга и DDoS.
- **Метрика:**
  - Неаутентифицированный: ≤ 60 RPS на IP
  - Аутентифицированный: ≤ 300 RPS на пользователя
- **Метод проверки:** нагрузочный тест (превышение лимита → 429 Too Many Requests)

### NFR-15: Хеширование телефонов

- **Требование:** Номера телефонов пользователей должны храниться в виде криптографического хеша (bcrypt / Argon2); в чате телефон не отображается без явного согласия продавца.
- **Метрика:** в БД поле `phone_hash` содержит хеш; raw телефон нигде не логируется
- **Метод проверки:** code review; тест API (поле телефона не возвращается в ответах чата)

### NFR-16: OWASP Top 10

- **Требование:** Система должна быть защищена от уязвимостей OWASP Top 10 (SQL injection, XSS, CSRF, IDOR и др.).
- **Метрика:** 0 критических и высоких уязвимостей по результатам penetration test до запуска MVP
- **Метод проверки:** pentest перед запуском; SAST в CI/CD pipeline

### NFR-17: PCI DSS соответствие

- **Требование:** Данные платёжных карт не должны храниться, обрабатываться или передаваться через инфраструктуру Carsale; всё — через PCI DSS-сертифицированный шлюз.
- **Метрика:** ни один сервер Carsale не входит в PCI scope; подтверждено SAQ A шлюза
- **Метод проверки:** аудит конфигурации; договор с Click/Payme подтверждает PCI DSS

## 5. Приватность и соответствие законодательству

### NFR-18: Локализация персональных данных (ЗРУ-547, ст. 8)

- **Требование:** Все персональные данные граждан Узбекистана (PII) должны храниться и обрабатываться исключительно на серверах, физически расположенных в юрисдикции Республики Узбекистан.
- **Метрика:** ни одна PII-запись не реплицируется в зарубежные облачные регионы
- **Метод проверки:** аудит конфигурации хостинга; документация от дата-центра (физическое местоположение в UZ)

### NFR-19: Регистрация оператора ПД

- **Требование:** Carsale должна быть зарегистрирована в реестре операторов персональных данных Агентства по персональным данным при Минюсте РУз до начала обработки данных пользователей.
- **Метрика:** свидетельство о регистрации оператора получено до MVP-запуска
- **Метод проверки:** наличие свидетельства в документации компании

### NFR-20: Согласие пользователя

- **Требование:** Система должна получать явное информированное согласие пользователя на каждый тип обработки ПД при регистрации (отдельный чекбокс на маркетинг).
- **Метрика:** форма согласия содержит раздельные чекбоксы для: (1) обработки ПД для работы сервиса, (2) маркетинговых коммуникаций; нажатие «Зарегистрироваться» без согласия на (1) невозможно
- **Метод проверки:** UI тест + правовой аудит Политики конфиденциальности

### NFR-21: Право на удаление данных

- **Требование:** Система должна позволять пользователю запросить удаление своих данных; запрос обрабатывается ≤ 15 рабочих дней (ЗРУ-547, ст. 19–22).
- **Метрика:** кнопка «Удалить аккаунт» присутствует в профиле; автоматический тикет на обработку; deadline 15 раб. дней
- **Метод проверки:** e2e тест + мониторинг SLA обработки

### NFR-22: Обезличивание данных при LLM-запросах

- **Требование:** При формировании запросов к внешним LLM API (Claude / OpenAI) персональные данные пользователей должны быть исключены или обезличены.
- **Метрика:** ни один запрос к LLM API не содержит phone, email, real_name или другие PII-поля
- **Метод проверки:** code review; автоматический scan LLM-запросов в тестах (assert no PII)

## 6. Совместимость

### NFR-23: Браузеры

- **Требование:** Система должна корректно работать в последних 2 версиях браузеров: Chrome, Firefox, Safari, Edge.
- **Метрика:** все P0 user flows проходят без ошибок в тестируемых браузерах
- **Метод проверки:** кросс-браузерное тестирование в BrowserStack или Playwright multi-browser

### NFR-24: Адаптивная вёрстка

- **Требование:** Интерфейс должен корректно отображаться и использоваться на устройствах с шириной экрана от 360px до 1440px+.
- **Метрика:** основные сценарии (каталог, карточка, форма размещения) работают без горизонтального скролла при 360px
- **Метод проверки:** Playwright viewport tests (360, 768, 1280, 1440)

---

## 7. Наблюдаемость

### NFR-25: Централизованное логирование

- **Требование:** Все сервисы должны писать структурированные логи (JSON) в централизованную систему (ELK / Loki); уровни: ERROR, WARN, INFO, DEBUG.
- **Метрика:** 100% сервисов отправляют логи в систему; retention ≥ 30 дней
- **Метод проверки:** проверка конфигурации при деплое

### NFR-26: Метрики и алертинг

- **Требование:** Система должна экспортировать метрики (RPS, latency p50/p95/p99, error rate, uptime) в Prometheus / Grafana; критические алерты — в Slack/PagerDuty.
- **Метрика:** alert срабатывает ≤ 1 мин после выхода за порог; дашборд с key metrics доступен 24/7
- **Метод проверки:** fire drill: намеренно превышаем порог → проверяем алерт

### NFR-27: Distributed tracing

- **Требование:** Запросы должны иметь сквозной trace ID для отладки межсервисных цепочек.
- **Метрика:** trace_id присутствует в заголовках всех HTTP-запросов между сервисами и в логах
- **Метод проверки:** проверка заголовков в интеграционных тестах

---

## 8. Локализация

### NFR-28: Двуязычный интерфейс

- **Требование:** Весь пользовательский интерфейс (labels, сообщения об ошибках, уведомления) должен быть доступен на узбекском (UZ) и русском (RU) языках с первого дня запуска.
- **Метрика:** 0 непереведённых строк в production; переключение языка — без перезагрузки страницы
- **Метод проверки:** i18n coverage check в CI; ручное тестирование оба языка в ключевых флоу

### NFR-29: Формат валюты и чисел

- **Требование:** Цены отображаются в узбекских сумах (UZS) с локализованным форматированием; опциональное отображение в USD по текущему курсу.
- **Метрика:** цены форматируются правильно (1 000 000 сум, не 1000000)
- **Метод проверки:** unit tests formatter; visual review
