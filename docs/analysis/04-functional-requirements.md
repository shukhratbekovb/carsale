# Carsale — Функциональные требования (SRS)

> Версия: 1.0 · Дата: 2026-06-28 · Источник: [PRD](../PRD.md) · Автор: Системный аналитик  
> Стандарт: ISO/IEC/IEEE 29148:2018

---

## 1. Обзор

Требования организованы по функциональным модулям, соответствующим приоритетам PRD (P0 / P1 / P2).  
Каждое требование содержит: уникальный ID, формулировку «система должна», источник (UC + цель PRD), acceptance criteria.

**Соглашения:**
- «Система должна» = обязательное требование
- «Система может» = желательное
- ID требований из PRD сохранены: FR-01 — FR-20

## 2. Модуль: Аутентификация и верификация

### FR-01: Регистрация и базовая верификация

- **Формулировка:** Система должна позволять незарегистрированному пользователю создать аккаунт путём ввода номера телефона и подтверждения SMS OTP.
- **Приоритет:** P0
- **Источник:** UC-03, G-5, BR-1
- **Входы:** номер телефона в формате +998XXXXXXXXX
- **Обработка:** валидация формата → запрос к Eskiz UZ API → генерация OTP (6 цифр, TTL 5 мин) → хранение OTP-хеша
- **Выходы:** аккаунт создан или идентифицирован; сессия установлена
- **Acceptance criteria:**
  - Дано: корректный номер телефона, когда: пользователь нажимает «Получить код», тогда: SMS с OTP доставляется за ≤ 30 сек
  - Дано: OTP введён правильно в течение 5 мин, тогда: сессия установлена, пользователь перенаправлен
  - Дано: OTP введён неверно 3 раза, тогда: сессия OTP блокируется на 15 мин, показывается соответствующее сообщение
  - Дано: незарегистрированный пользователь, когда: пытается разместить объявление, тогда: система требует регистрацию
- **Зависимости:** Eskiz UZ API (ADR-001)

### FR-02: Верификация через OneID (P1)

- **Формулировка:** Система должна позволять продавцу пройти расширенную верификацию личности через OneID (gov.uz) и получить статус «Проверен».
- **Приоритет:** P1
- **Источник:** UC-14, G-5, BR-7
- **Входы:** инициация OneID OAuth-flow из профиля продавца
- **Обработка:** OAuth redirect → OneID подтверждает личность → система сохраняет статус верификации
- **Выходы:** статус «Проверен» присвоен; бейдж отображается на профиле и в объявлениях
- **Acceptance criteria:**
  - Бейдж «Проверен» отображается на карточке продавца и на каждом его объявлении после успешной верификации
  - Верифицированные объявления имеют приоритет в сортировке по умолчанию при равных прочих условиях
  - При OneID-верификации, включающей фото лица, пользователю показывается явное согласие на биометрическую обработку
- **Зависимости:** Партнёрство с OneID (gov.uz) — открытый вопрос OQ-4

## 3. Модуль: Управление объявлениями

### FR-03: Авто-блюр госномера и VIN на фото (ML)

- **Формулировка:** Система должна автоматически детектировать и замазывать государственный регистрационный знак и VIN на каждом загруженном фото до публикации объявления.
- **Приоритет:** P0
- **Источник:** UC-09 (include в UC-08), G-6, BR-3, BR-4
- **Входы:** загруженный файл изображения (JPEG/PNG, ≤ 10 МБ)
- **Обработка:** CV-модель детектирует bounding box госномера/VIN → применяет Gaussian blur или заливку → генерирует blurred-версию
- **Выходы:** URL blurred-версии фото; оригинал хранится внутри (недоступен покупателям)
- **Acceptance criteria:**
  - ≥ 95% государственных номеров на тестовой выборке замазаны без ручного вмешательства
  - Обработка одного фото занимает ≤ 5 сек
  - Продавец видит превью с блюром до сохранения и может вручную скорректировать область блюра
  - На публикуемых фото присутствует только blurred-версия; оригинал не доступен через публичный API
- **Зависимости:** ML-инфраструктура (ADR-006), FR-02 (объявления могут размещать только аутентифицированные)

### FR-04: Размещение объявления с AI-подсказкой цены

- **Формулировка:** Система должна предоставить продавцу форму размещения объявления и до публикации показать рекомендованный ценовой диапазон от AI.
- **Приоритет:** P0
- **Источник:** UC-08, G-1, G-3, BR-5
- **Входы:** марка, модель, год (1990–текущий), пробег (0–999 999 км), состояние, цвет, КПП, привод, объём двигателя, цена (UZS), описание, город, фото (1–20 штук)
- **Обработка:** валидация → сохранение черновика → ML Deal Rating (FR-05) → проверка фрода (FR-07) → публикация или модерация
- **Выходы:** объявление в статусе «Опубликовано» или «На модерации»; продавец видит рекомендованный диапазон
- **Acceptance criteria:**
  - Все обязательные поля (марка, модель, год, пробег, цена, город, ≥ 1 фото) валидируются перед отправкой
  - Объявление проходит модерацию ML и публикуется ≤ 30 мин с момента отправки (при отсутствии фрод-флага)
  - Продавец видит рекомендованный ценовой диапазон до публикации
  - Форма доступна только аутентифицированным пользователям (BR-1)
- **Зависимости:** FR-03, FR-05, FR-07

### FR-05: Управление объявлениями продавца

- **Формулировка:** Система должна предоставить продавцу личный кабинет для просмотра, редактирования, обновления цены и снятия своих объявлений.
- **Приоритет:** P0
- **Источник:** UC-12, G-3
- **Входы:** действия продавца: редактировать, снять с публикации, удалить, обновить цену
- **Обработка:** обновление данных; при изменении цены — пересчёт Deal Rating (FR-06)
- **Выходы:** обновлённое объявление; уведомление (FR-11)
- **Acceptance criteria:**
  - Продавец видит список своих объявлений со статусом (Черновик / На модерации / Опубликовано / Снято)
  - При изменении цены Deal Rating пересчитывается автоматически и обновляется в течение 1 мин
  - Продавец может снять/удалить объявление в любой момент

## 4. Модуль: Каталог и поиск

### FR-06: Каталог объявлений с фильтрами

- **Формулировка:** Система должна отображать каталог активных объявлений с фильтрацией и сортировкой без перезагрузки страницы.
- **Приоритет:** P0
- **Источник:** UC-01, G-3, G-4
- **Входы:** фильтры (марка, модель, год от/до, цена от/до, пробег от/до, тип КПП, привод, Deal Rating, город, статус «Проверен»); сортировка (дата, цена, Deal Rating)
- **Обработка:** построение запроса к БД/поиску → пагинация (≥ 20 объявлений на страницу) → возврат результатов
- **Выходы:** список карточек объявлений с мета-данными (фото, марка, модель, год, цена, Deal Rating, бейдж)
- **Acceptance criteria:**
  - Фильтры применяются без перезагрузки страницы (AJAX / SSR partial update)
  - Время загрузки каталога ≤ 2 сек на соединении 4G (≥ 10 Мбит/с)
  - При нулевых результатах отображается блок «Похожие объявления» (смягчённые фильтры)
  - Сортировка «Сначала выгодные» показывает объявления с Deal Rating «Отличная сделка» первыми
- **Зависимости:** FR-07 (Deal Rating присвоен до каталога)

### FR-07: Страница объявления (карточка авто)

- **Формулировка:** Система должна отображать детальную страницу объявления со всеми характеристиками, Deal Rating, ML-флагами и кнопкой связи с продавцом.
- **Приоритет:** P0
- **Источник:** UC-02, G-3, G-6, BR-13
- **Входы:** listing_id
- **Обработка:** загрузка данных объявления, ML-результатов, статуса продавца; проверка аутентификации пользователя для кнопки «Написать»
- **Выходы:** страница с полной информацией
- **Acceptance criteria:**
  - Страница загружается ≤ 2 сек
  - Deal Rating и ML-флаги загружаются **вместе** с карточкой (не после, не lazy)
  - Mileage Flag отображается с tooltip-пояснением «что именно детектировано»
  - Кнопка «Написать» доступна только аутентифицированным пользователям; Гость видит «Войдите, чтобы написать»
  - Событие `listing_viewed` трекается при каждом просмотре

### FR-08: NLP-поиск (P1)

- **Формулировка:** Система должна принимать поисковые запросы на естественном языке и возвращать релевантные объявления.
- **Приоритет:** P1
- **Источник:** UC-04, G-3
- **Входы:** текстовый запрос (UZ или RU): «надёжный семейный авто до $10 000 с автоматом»
- **Обработка:** LLM API извлекает параметры → конвертация в структурированные фильтры → запрос к каталогу
- **Выходы:** отфильтрованный список объявлений; применённые фильтры показаны пользователю
- **Acceptance criteria:**
  - Время ответа NLP-поиска ≤ 2 сек
  - Система корректно извлекает цену, тип КПП, характеристики из типичных запросов (manual smoke test)
  - Если запрос не может быть интерпретирован — fallback на классический поиск с сообщением «Уточните запрос»
- **Зависимости:** LLM API; накопленные поведенческие данные для улучшения точности

## 5. Модуль: ML-функции

### FR-09: Deal Rating — AI-оценка цены (ML)

- **Формулировка:** Система должна автоматически присваивать каждому опубликованному объявлению метку Deal Rating на основе сравнения с аналогами.
- **Приоритет:** P0
- **Источник:** UC-10, G-4, G-6, BR-5
- **Входы:** характеристики объявления (марка, модель, год, пробег, состояние, регион, цена)
- **Обработка:** ML-модель (градиентный бустинг) вычисляет медианную рыночную цену → сравнивает с ценой продавца → присваивает метку
- **Выходы:** DealRatingLabel (GREAT_DEAL | FAIR_PRICE | OVERPRICED), recommendedPriceMin, recommendedPriceMax
- **Acceptance criteria:**
  - Deal Rating присвоен ≥ 95% активных объявлений
  - MAPE модели ≤ 15% на тестовой выборке
  - Метка обновляется при изменении цены продавцом в течение ≤ 1 мин
  - Продавец видит рекомендованный диапазон; покупатель видит только метку (не числовой скор)
- **Зависимости:** seed-датасет (ADR-003); ML-инфраструктура

### FR-10: Детекция скрученного пробега (ML)

- **Формулировка:** Система должна флаговать объявления с аномальным пробегом (несовместимым с годом выпуска или историей предыдущих объявлений по VIN/госномеру).
- **Приоритет:** P0
- **Источник:** UC-08 (include), G-6, BR-10
- **Входы:** год выпуска, заявленный пробег, история предыдущих объявлений по VIN/госномеру в БД
- **Обработка:** сравнение пробега с ожидаемым диапазоном (средний пробег/год × возраст) + сравнение с предыдущими объявлениями
- **Выходы:** mileage_flag (boolean), mileage_flag_reason (string)
- **Acceptance criteria:**
  - Флаг отображается на карточке объявления (покупателю) и виден до и после публикации
  - False positive rate ≤ 5% на размеченном тестовом наборе
  - При повторном объявлении того же VIN/госномера с меньшим пробегом — автоматический флаг (BR-10)
  - Tooltip объясняет: «Пробег ниже, чем в предыдущем объявлении с этим номером»

### FR-11: Детекция фрода и дублей (ML)

- **Формулировка:** Система должна автоматически детектировать мошеннические объявления (дубли фото, аномальная цена) и скрывать их до проверки модератором.
- **Приоритет:** P0
- **Источник:** UC-08, UC-15, G-6, BR-2, BR-11, BR-12
- **Входы:** фото объявления (image hash), цена, рыночная медиана из FR-09
- **Обработка:**
  - Дубли: perceptual hash фото сравнивается с хешами активных объявлений; совпадение → fraud_flag
  - Ценовая аномалия: цена < 40% медианы → fraud_flag с причиной «too_good_to_be_true»
- **Выходы:** fraud_flag (boolean), fraud_reason, статус объявления → «На модерации»
- **Acceptance criteria:**
  - Дубли определяются ≤ 1 мин после публикации
  - Доля фрод-объявлений, ставших видимыми покупателям, < 0.5% от общего числа
  - Продавец-владелец видит сообщение о причине: «Подобное фото используется в другом объявлении»
- **Зависимости:** FR-09 (медиана цены нужна для порогового сравнения)

## 6. Модуль: Коммуникация

### FR-12: Внутренний чат

- **Формулировка:** Система должна обеспечить внутренний чат между продавцом и покупателем без раскрытия номера телефона.
- **Приоритет:** P0
- **Источник:** UC-06, G-3, G-6, BR-13
- **Входы:** текстовое сообщение (≤ 2 000 символов)
- **Обработка:** создание ChatThread (если не существует) → сохранение Message → отправка уведомления получателю
- **Выходы:** сообщение доставлено; уведомление отправлено; история чата сохранена
- **Acceptance criteria:**
  - Сообщение доставляется в интерфейс получателя ≤ 3 сек
  - Push/email уведомление отправляется при получении нового сообщения
  - История чата сохраняется бессрочно (пока объявление не удалено)
  - Номер телефона не отображается в чате без явного согласия продавца (BR-13)

### FR-13: Уведомления

- **Формулировка:** Система должна отправлять email и push (браузерные) уведомления по ключевым событиям.
- **Приоритет:** P0
- **Источник:** UC-13, G-3
- **Входы:** событие (новое сообщение, снижение цены, статус объявления)
- **Обработка:** выбор канала (push / email) → генерация контента → отправка через Firebase/WebPush + SendGrid/SES
- **Выходы:** уведомление доставлено; статус доставки записан
- **Acceptance criteria:**
  - Уведомление доставляется ≤ 1 мин после события
  - Пользователь может отключить каждый тип уведомлений отдельно в настройках профиля
  - Типы событий: новое сообщение в чате, снижение цены на сохранённое авто ≥ 3% (P1), статус объявления (опубликовано / на модерации / отклонено)

## 7. Модуль: Оплата

### FR-14: Приём платежей

- **Формулировка:** Система должна принимать оплату за публикацию объявления и/или расширенный отчёт через платёжные шлюзы Click и/или Payme.
- **Приоритет:** P0 (инфраструктура; монетизация вводится в Фазе 1)
- **Источник:** UC-11, G-2, BR-6
- **Входы:** сумма, тип действия (публикация / отчёт), выбранный шлюз
- **Обработка:** создание платёжного ордера → redirect на страницу шлюза → обработка webhook → обновление статуса
- **Выходы:** Payment со статусом SUCCESS или FAILED; квитанция на email
- **Acceptance criteria:**
  - Успешный платёж обрабатывается ≤ 5 сек с момента получения webhook
  - Квитанция отправляется на email немедленно после подтверждения
  - При ошибке шлюза — понятное сообщение пользователю с возможностью повторить
  - Данные карт не хранятся на серверах Carsale (BR-6); PCI DSS compliance — через шлюз

## 8. Модуль: История авто (P1)

### FR-15: Расширенный отчёт по VIN / госномеру

- **Формулировка:** Система должна генерировать платный расширенный отчёт об истории автомобиля на основе данных ГУБДД, страховых компаний и таможни.
- **Приоритет:** P1
- **Источник:** UC-07, G-6
- **Входы:** VIN или госномер автомобиля
- **Обработка:** запрос к API ГУБДД + страховым компаниям + ГТК → агрегация данных → генерация отчёта
- **Выходы:** структурированный отчёт: кол-во страховых случаев, штрафы, пробег на таможне
- **Acceptance criteria:**
  - Отчёт генерируется ≤ 10 сек
  - При отсутствии данных — честный ответ «Данные не найдены», без пустых секций
  - Доступен только после оплаты (FR-14)
- **Зависимости:** B2G-партнёрство с ГУБДД и страховыми компаниями (открытый вопрос OQ-1); статус: TBD, критический путь Фазы 1

## 9. Модуль: Избранное и алерты (P1)

### FR-16: Избранное, сохранённые поиски и алерты снижения цены

- **Формулировка:** Система должна позволять покупателю сохранять объявления в избранное, сохранять поисковые запросы и получать уведомления о снижении цены.
- **Приоритет:** P1
- **Источник:** UC-05, G-3, BR-9
- **Входы:** action (сохранить/удалить из избранного), search_query с фильтрами
- **Выходы:** список избранного; уведомление при снижении цены ≥ 3% на сохранённое объявление
- **Acceptance criteria:**
  - Избранное сохраняется между сессиями (привязано к аккаунту, не cookie)
  - Алерт снижения цены ≥ 3% отправляется ≤ 1 час после изменения цены (BR-9)
  - При появлении новых объявлений по сохранённому поиску — уведомление в течение 1 часа

## 10. Модуль: LLM-функции (P1)

### FR-17: Авто-генерация описания и перевод (LLM)

- **Формулировка:** Система должна предлагать продавцу автоматически сгенерированное описание объявления и автоматический перевод RU↔UZ.
- **Приоритет:** P1
- **Источник:** FR-16 PRD, G-1
- **Входы:** характеристики авто (марка, модель, год, пробег, состояние, особенности), целевой язык
- **Обработка:** запрос к LLM API с обезличенными данными (без PII — BR-8) → возврат текста → редактирование продавцом
- **Выходы:** предзаполненное поле описания; переведённая версия
- **Acceptance criteria:**
  - Генерация описания ≤ 5 сек
  - Продавец может редактировать результат перед публикацией
  - Перевод сохраняет технические термины и смысл
  - PII (телефон, email) не передаётся в LLM-запросе (BR-8)

### FR-18: Чат-бот ассистент на карточке авто (LLM)

- **Формулировка:** Система должна предоставить встроенного LLM-чат-бота на карточке объявления для ответов на вопросы покупателя.
- **Приоритет:** P1
- **Источник:** FR-17 PRD, G-3
- **Входы:** вопрос покупателя об автомобиле
- **Обработка:** запрос к LLM с контекстом объявления (характеристики, модель авто) → ответ
- **Выходы:** ответ бота ≤ 3 сек; если не знает — предложение написать продавцу
- **Acceptance criteria:**
  - Бот отвечает за ≤ 3 сек
  - При неизвестном ответе: «Не знаю, рекомендую спросить продавца» → кнопка «Написать»
  - PII не передаётся в LLM-запросе (BR-8)

## 11. Модуль: B2B и инфраструктура (P2)

### FR-19: Кабинет дилера

- **Формулировка:** Система должна предоставить дилерам отдельный интерфейс: массовая загрузка объявлений, аналитика портфеля, статус «Официальный дилер».
- **Приоритет:** P2
- **Источник:** FR-19 PRD, G-2
- **Acceptance criteria:**
  - Дилер загружает ≤ 500 объявлений за одну CSV-операцию
  - Аналитика (просмотры, контакты, конверсия) обновляется в реальном времени

### FR-20: Оценка повреждений по фото (ML, P2)

- **Формулировка:** Система должна анализировать фото авто и отображать видимые повреждения (царапины, вмятины, ржавчина).
- **Приоритет:** P2
- **Источник:** FR-18 PRD
- **Acceptance criteria:**
  - Precision детекции повреждений ≥ 80%
  - Результат отображается как визуальный отчёт на карточке
- **Зависимости:** размеченный датасет повреждений (отдельный проект сбора данных)

### FR-21: Инфраструктура для CIS-экспансии

- **Формулировка:** Система должна поддерживать мультирегиональную архитектуру с абстракцией источников данных по стране.
- **Приоритет:** P2
- **Источник:** FR-20 PRD
- **Acceptance criteria:**
  - Добавление нового региона не требует изменения бизнес-логики, только конфигурации источников данных и i18n
