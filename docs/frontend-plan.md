## 1. Контекст продукта (сводка из PRD)

- **Продукт:** веб-маркетплейс купли-продажи авто в Узбекистане с дифференциатором «доверие через данные»: Deal Rating (AI-оценка цены), детекция скрученного пробега, антифрод, авто-блюр номеров.
- **Рынок:** UZ-first, Ташкент на старте; интерфейс UZ + RU с первого дня (NFR-28).
- **Платформа:** только веб, адаптивная вёрстка 360–1440px+ (ADR-005) — мобильного приложения в MVP нет, поэтому мобильный браузер обязан давать полноценный опыт.
- **Роли фронтенда:** Гость, Покупатель, Продавец, Верифицированный продавец, Администратор (Дилер — P2).
- **North Star:** % объявлений, проданных за 30 дней. Frontend влияет через скорость каталога, доверие к Deal Rating/флагам и низкое трение при размещении объявления.

## 3. Технологический стек

| Слой | Выбор | Комментарий |
|------|-------|-------------|
| Framework | **Next.js 14+ App Router**, React Server Components по умолчанию | Уже зафиксировано в `analysis/09-architecture.md` контейнере Web Application |
| Язык | TypeScript (strict) | `typecheck-strict` — обязательный CI-гейт профиля |
| Стили | Tailwind CSS + design tokens | Токены нужны отдельно для Deal Rating цветовой семантики (см. §6) |
| UI-примитивы | shadcn/ui / Radix primitives | Копируемые компоненты, не runtime-зависимость — не ломает RSC |
| Клиентский state | Zustand / Jotai | Redux — только если уже есть обоснованный прецедент (anti-pattern профиля: `redux-without-justification`) |
| Серверный state | RSC + Server Actions | Формы размещения объявления, оплата, публикация — через Server Actions где возможно |
| Данные (client-only) | React Query | Для чата, уведомлений, real-time списков — того, что живёт вне RSC-дерева |
| Формы | React Hook Form + Zod | Форма объявления (FR-02) — самая тяжёлая форма продукта, обязателен строгий schema-валидатор |
| Иконки | lucide-react, **именованные импорты** | Анти-паттерн профиля: `default-imports-for-icons` — убивает tree-shaking |
| Тесты | Vitest + React Testing Library + Playwright (e2e) | Playwright также покрывает NFR-23 (кросс-браузер) и NFR-24 (вьюпорты) |
| i18n | next-intl (или аналог с RSC-поддержкой) | UZ/RU с первого дня, переключение без перезагрузки (NFR-28) |
| WebSocket клиент | Socket.IO client | Согласовано с WebSocket Hub в `analysis/09-architecture.md` (чат, real-time) |

### Анти-паттерны, которых явно избегать на этом профиле

- `use-client-everywhere` — убивает ценность RSC; `'use client'` только там, где реально нужна интерактивность
- `csr-only-on-seo-routes` — **killer для этого проекта**: каталог и карточка объявления обязаны рендериться на сервере (SSR/RSC), иначе теряется SEO-цель ADR-005
- `css-in-js-runtime` (styled-components runtime) — ломает RSC
- `global-state-in-context-everywhere` — server state вверх, props вниз; Context — только для дерева, не для всего приложения

## 6. Компонентная архитектура и дизайн-система

### Ключевые доменные компоненты (client vs server)

| Компонент | Тип | Особенность |
|-----------|-----|--------------|
| `ListingCard` | Server (RSC) | Deal Rating badge + бейдж «Проверен» + флаг пробега — рендерятся вместе с карточкой, **не lazy** (жёсткое acceptance criteria FR-07: «ML-флаги загружаются вместе с карточкой, не после») |
| `DealRatingBadge` | Server | Цветовой индикатор (зелёный/серый/красный) **+ текстовая метка** — PRD прямо запрещает голую иконку без пояснения (§5.3 UX) |
| `MileageFlagTooltip` | Client (interactive tooltip) | Клавиатурно доступен (focus + Enter), не только hover |
| `PhotoUploadWizard` | Client | Превью блюра, ручная корректировка области (FR-03 alt-flow), progress-индикатор ≤5 сек ожидания |
| `PriceEstimateWidget` | Client + Server Action | Запрос к ML Deal Rating, состояние `UNAVAILABLE` как валидный UI-стейт (см. §9) |
| `CatalogFilters` | Client (islands в RSC-странице) | Без перезагрузки страницы (FR-04); синхронизация с URL query для SSR-совместимости и шаринга ссылок |
| `ChatWindow` / `ChatThreadList` | Client + WebSocket | Real-time, офлайн-очередь сообщений (alt-flow UC-06: «сеть недоступна → сообщение в очереди») |
| `LanguageSwitcher` | Client | UZ/RU, без reload (NFR-28) |
| `VerifiedBadge` | Server | Бейдж «Проверен» — переиспользуется в карточке, профиле продавца, объявлении |
| `NotificationBell` | Client | Real-time счётчик непрочитанных |

### Design tokens

- Цветовая семантика Deal Rating: `great-deal` (зелёный), `fair-price` (серый), `overpriced` (красный) — тройка должна пройти contrast-check (WCAG AA, 4.5:1) на обоих языках интерфейса и в обеих цветовых темах, если тёмная тема предусмотрена.
- Типографика: обязательна проверка покрытия глифов для **узбекского языка** (латиница расширенная + кириллица используется параллельно на рынке) — не все Google Fonts покрывают узбекскую латиницу с диакритикой (oʻ, gʻ). Проверить перед выбором шрифта.
- Атомарная организация (Brad Frost): primitives (shadcn) → domain atoms (Badge, Flag, PriceTag) → molecules (ListingCard, FilterBar) → templates (CatalogLayout, ListingPageLayout).

## 7. i18n (NFR-28, NFR-29)

- UZ + RU с первого дня, переключатель в шапке, **без перезагрузки страницы**.
- CI-гейт: 0 непереведённых строк (i18n coverage check) — эквивалент `bundlewatch` для локализации, должен быть в пайплайне с первого спринта, а не добавляться в конце (иначе — типовой риск затягивания перевода перед лончем).
- Форматирование чисел/валют (NFR-29): утилита форматирования сумов (`1 000 000 сум`, не `1000000`); опциональный курс USD.
- RSC-совместимость: next-intl (или эквивалент) должен поддерживать server components — проверить до scaffolding, это блокирующее решение для всей архитектуры страниц.

## 8. Производительность

- **Изображения:** `next/image` для всех фото; blurred-версии раздаются через CDN (edge в Ташкенте, NFR-8, p95 ≤ 500мс); thumbnail pipeline — на бэкенде/ML-сервисе, фронтенд потребляет уже готовые размеры.
- **Bundle budget:** 150 KB gzip/маршрут — главный риск: `/sell/new` (тяжёлый wizard с фото-аплоадом) и `/chat` (WebSocket клиент). Обе страницы — кандидаты на `dynamic import` тяжёлых under-the-fold частей.
- **Критическое ограничение (конфликт с типичной перф-оптимизацией):** Deal Rating и ML-флаги (пробег, фрод) **обязаны** приходить вместе с первым рендером карточки/страницы объявления (жёсткое acceptance criteria FR-07 и NFR-2). Стандартный перф-паттерн «дозагрузить второстепенное после LCP» здесь **запрещён продуктовым требованием** — эти данные не второстепенны, они и есть УТП продукта. Решение: включать ML-результаты в тот же SSR-запрос/RSC fetch, что и данные объявления (параллельный `Promise.all` на сервере), а не отдельный client-side fetch после гидратации.
- **PWA** (компенсирующая мера ADR-005): manifest, offline-кэш статики, «добавить на главный экран» — частично закрывает отсутствие нативного приложения.
- **Мониторинг:** Core Web Vitals в RUM (не только синтетика Lighthouse CI) — особенно LCP на реальных 3G/4G соединениях UZ, поскольку синтетический throttle не всегда отражает реальные сети местных операторов.

## 9. Обработка деградации внешних сервисов (frontend UX для error/edge states)

Frontend обязан явно отрисовывать не только happy path, но и все alt/exception-потоки из `analysis/06-sequence-diagrams.md` и `analysis/07-process-and-state.md` — это часть acceptance criteria, не «технический долг на потом»:

| Ситуация | UI-состояние |
|----------|-------------|
| ML-сервис недоступен (Deal Rating timeout > 1с) | Метка «Оценка недоступна» вместо пустого места или бесконечного спиннера (state `UNAVAILABLE`) |
| Блюр-сервис недоступен | Явное предупреждение «Автоблюр временно недоступен», ручная разметка обязательна перед сохранением |
| Eskiz SMS недоступен | «Не удалось отправить SMS, попробуйте позже» + retry через 60 сек, а не generic error |
| 3 неверных OTP | Блокировка 15 мин с явным таймером обратного отсчёта |
| Оплата отклонена | Понятная причина + кнопка повторить/сменить шлюз (не redirect в никуда) |
| Сеть недоступна при отправке сообщения в чате | Сообщение остаётся в UI как «отправляется», ретрай при восстановлении сети (optimistic UI + queue) |
| Нулевые результаты каталога | Блок «Похожие объявления» вместо пустой страницы |

## 10. Тестирование и CI

- **Unit/компонентные:** Vitest + React Testing Library — обязательны для всех доменных компонентов из §6, особенно `DealRatingBadge`, `PriceEstimateWidget` (все три состояния: GREAT_DEAL/FAIR_PRICE/OVERPRICED/UNAVAILABLE).
- **E2E (Playwright):** P0 flows, зеркалирующие `analysis/06-sequence-diagrams.md`: регистрация (§6.1, включая error-ветки), размещение объявления (§6.2 + fraud-путь §6.3), чат (§6.4), оплата (§6.5), каталог (§6.6).
- **Кросс-браузер (NFR-23):** Playwright projects — Chrome, Firefox, Safari, Edge, последние 2 версии.
- **Вьюпорты (NFR-24):** Playwright viewport-тесты на 360 / 768 / 1280 / 1440 — без горизонтального скролла на ключевых сценариях (каталог, карточка, форма объявления).
- **A11y:** axe-core в CI на каждый PR, Lighthouse a11y ≥ 95 — закрывает пробел WCAG из §2.
- **Perf:** Lighthouse CI + bundlewatch на каждый маршрут, блокирующий гейт при регрессии бюджета.
